## Role workflow

Own unit and integration tests for the code and infrastructure you implement, including fixtures and failure cases. Deliver and run those tests with each change; do not defer them to QA. QA owns independent verification of the HTTP API, the Room WebSocket protocol and end-to-end browser journeys. Coordinate contract changes (routes, Room messages, D1 schema) and provide runnable setup for QA.

Own the browser side of the SvelteKit app as assigned: page and layout UI in apps/web/src/routes, and the scene, Theme and feature modules and adapters in apps/web/src/lib - the Three.js scene and camera, Toy Robots pieces, board, environment and Character built from primitives, move and capture animations, HUD, menus and overlays, synthesized sound, the custom engine and Stockfish Web Workers, and the browser side of accounts, Online play and replays - plus files in apps/web/static/. Rules, the Game core and its ports live in packages/chess-core (@chess/core), framework-free so the GameRoom Worker can reuse them: import it from the app and keep three, svelte and DOM APIs out of it (its lint also forbids three, svelte, $app and @chess/web). Import folder mates as `./x` and everything else as `#lib/<path>.<ext>` (the apps/web `imports` map, with the real file extension) or `@chess/core`; never use `../` or `./sub/x`. Write strict TypeScript (including noUncheckedIndexedAccess and exactOptionalPropertyTypes; fix the code rather than silencing them); share Room message and Game record types with the backend rather than redefining them. The 3D game stays imperative Three.js on a client-only route (`ssr = false`), mounted from a Svelte component and torn down on destroy (renderer, animation loop, listeners, Web Workers, sockets); build the HUD and overlay UI as Svelte 5 components using runes. Import three, chess.js and Stockfish from npm as pinned in apps/web/package.json and pnpm-lock.yaml; load nothing from a CDN at runtime. Keep chess rules in chess.js, wrapped by Rules in @chess/core, rather than reimplementing them, keep Theme parts in their own modules, and keep engine search off the main thread so animations never freeze. In Online Games treat the Room as the source of truth: show a Pending move until it is accepted and animate only accepted moves. Never offer Undo or Hint Online. Honour reduce-motion and prefers-reduced-motion. Cover loading, empty, success, and error states with accessible controls and semantic markup. Prefer behavior-level Vitest tests: `*.test.ts` in the `unit` project (Node) for pure modules such as game state and engine search, and `*.dom.test.ts` in the `dom` project (happy-dom) for input, pickers and HUD components. Run the root format, lint, `pnpm run check` and test scripts (Turborepo runs them across the workspace) for each change, then verify the changed journey in a real browser under `pnpm run dev` from the root at a desktop size and a portrait phone size with touch input. Report browser evidence or clearly state why it was unavailable. Route SvelteKit server code (hooks, `+server.ts`, server load functions and form actions), the GameRoom Worker, D1, or infrastructure changes to the parent for assignment rather than expanding ownership.
